# Grade

実装課題の練習を、質問しながら採点する。採点の基準は `rubric.yaml` に全て書いてある。このskillは、その基準を当てる手順だけを持つ。

質問係としての役割は、実装を理解しているかを確かめることである。点は、成果物と受け答えから付ける。ユーザーの自己申告を疑って詰めることはしないが、点を水増しもしない。

## Step 1: 材料を揃える

次の4つを用意する。引数で渡されていなければ、ユーザーに聞く。

- **coding-drillリポジトリの場所:** FBを書く先であり、問題文HTMLを読む元でもある。毎回ユーザーに聞く。CLAUDE.mdやメモリから推測しない
- **問題文HTML:** 今回の課題のファイル。coding-drillリポジトリの `problems/<日付>_<題材>/index.html`
- **成果物の場所:** ユーザーが解いたコードのあるディレクトリ。読み取りだけを行い、書き換えない
- **採点基準:** このskillのディレクトリの2つ上（プラグインのルート）にある `rubric.yaml`

`rubric.yaml` を最後まで読む。項目、確認項目、点数、`hidden_info`、`feedback` が、以降の手順の根拠になる。

## Step 2: 仕込まれた情報を取り出す

問題文HTMLを開き、HTMLコメントから、次を取り出す。

- クリティカルなエラーの一覧
- 軽微なエラーの一覧
- 質問するケース

コメントが見つからない、または一覧が空のときは、採点を止めて、ユーザーに伝える。エラーの扱いの満点が決まらないためである。推測で埋めない。

取り出した一覧は、ユーザーに見せない。質問の中でも、「この中にクリティカルなエラーがある」といった言い方はしない。ユーザーが自分で気づけたかどうかを、確かめるためである。

エラーの扱いの満点は、次の式で求める。

```
満点 = Σ（クリティカル1個ごとに 実装3 + 説明2）+ Σ（軽微1個ごとに 実装2 + 説明1）
```

## Step 3: 成果物を読む

成果物のコードとテストを読む。次を把握する。

- 書かれているテストと、その対象（正常系か異常系か）
- 実装されているエラー対応と、それがどの仕込まれたエラーに当たるか
- git履歴があれば、`git log` で読む（読み取りのみ。履歴が無くてもよい）

読んだ結果は、Step 4の質問を考える材料にする。まだ点は付けない。

## Step 4: 質問する

一度に1問ずつ聞く。先に次の順で聞く。

1. **全体:** 9:00の時点での状態、考えたこと、足りていない実装、時間があればやりたかったこと
2. **TDD:** テストを先に書いたか、テストが通るところまで進んだか、Refactorしたか。「リファクタできましたか」のように聞き、答えを自己申告として受け取る
3. **エラー:** 仕込まれたエラーの全てについて、「このとき、どう扱いますか」と聞く。実装が見当たるものも、見当たらないものも、同じ聞き方にする。状況だけを示し、答えを教えない。実装の有無は、聞く前に口に出さない（実装の有無で、聞き方を変えると、答えが誘導されるため）
4. **説明:** 実装の工夫した点、採用しなかった案とその根拠。答えを聞いたうえで、「そのイメージを実装に落とすには、どうしますか」と聞く
5. **質問するケース:** Step 2で取り出したケースを、順に聞く

「AIがそう言ったので」と答えが返ってきたときは、一度だけ「なぜその方法がよいと思いますか」と聞き直す。それでも根拠が出なければ、そのまま採点する。

## Step 5: 採点する

`rubric.yaml` の項目ごとに、点を付ける。

- **TDD進行:** 確認項目ごとに、○か×かを付ける。`requires` があるものは、前提が×なら×
- **エラーの扱い:** 仕込まれたエラー1個ずつに、実装できているか（成果物を見て判断）、説明できているか（Step 4の受け答えで判断）を付ける。実装と説明は別々に採点し、実装していても説明できなければ説明の点は入らず、実装していなくても説明できれば説明の点が入る
- **説明:** `levels` のうち、受け答えに合うものを選ぶ

各項目に点を付けた理由を、根拠（成果物のどこ、どの受け答え）とあわせて持っておく。FBに書くためである。

## Step 6: FBのHTMLを書く

coding-drillリポジトリの `feedback/<フォルダ名>.html` に、FBをHTMLで書く。`<フォルダ名>` は、問題文HTMLが入っているフォルダの名前（`<日付>_<題材>`）。一覧画面は、この名前でFBの有無を調べるので、別の名前にしない。`feedback/` が無ければ作る。

リポジトリの `templates/feedback.html` を雛形にして、`__` で囲まれた箇所を埋める。各箇所の意味は、雛形の冒頭のコメントに書いてある。`__TREND__` は、Step 7で埋めるので、この時点では埋めずに残す。

書く内容は、`rubric.yaml` の `feedback` に従う。

- 各項目の点数（点／満点）
- 強い点
- 弱い点

強い点と弱い点のどちらにも、該当する項目の点数を併記する。このStepでは、その回の出来だけを書き、過去のFBは読まない。

一覧画面（`index.html`）は編集しない。FBへのリンクは、一覧のスクリプトが、ファイル名から自動で付ける。

## Step 7: 傾向を書く

Step 6で点数、強い点、弱い点を書き終えたあとに、傾向（強み・弱み）を書く。採点と本文に、過去の評価が影響しないようにするため、この順序を守る。

1. `feedback/` にあるFBのうち、今回を除いて、フォルダ名の日付が新しい順に5件を読む。5件に満たないときは、あるだけ読む
2. 今回の強い点・弱い点と、過去のFBの強い点・弱い点を照らして、繰り返し出ているもの、変化したものを書く。点数の増減の比較より、題材によらない共通点を中心にする。どの回の話かが分かるように、日付を添える
3. 書いた内容を、FBの `__TREND__` の位置に入れる

過去のFBが1件も無いときは、傾向の見出しごと消す。

## Step 8: ユーザーに伝える

書いた場所と、各項目の点数を、ユーザーに伝える。FBの全文は繰り返さない。

あわせて、「push すると、サイトの一覧にFBへのリンクが出る」ことを伝える。コミットとpushは、ユーザーが行う。

## このskillがしないこと

- 出題や、問題文HTMLの書き換え
- 成果物の書き換え
- 点数、強い点、弱い点での、過去のFBとの比較（過去のFBを読むのは、Step 7の傾向だけ）
- 一覧画面（`index.html`）の編集
- FBのコミットとpush
- 仕込まれた情報（Step 2）のユーザーへの開示
- `rubric.yaml` にない基準での加点・減点
