# レビュー規約

developmentプラグインのskillが、レビューで使う基準をまとめる。基準の値はこのファイルだけに書き、skillはここを読んで判定する。

# PRの品質基準となる要素

1. PRに含まれる「問題解決」の数
2. PRの行数および文字数

# PRに含まれる「問題解決」の数

PRは、ある問題(issue)に対する「問題解決」である。
1つのPRには、1つの「問題解決」と、「問題解決」を成り立たせるための軽微な調整がいくつか(3個程度まで)だけ入っているべき。

PRを読んで、「問題解決」が2つ以上入っていた場合は、「問題解決の混在」とする。

# PRの大きさの上限

「問題解決」が1つだけの場合でも、変更量が膨大なPRはレビュー負荷が高く、PR品質を保ちにくい。
そのような「問題解決」に対しては、さらに詳細な「問題解決」に分割可能かを検討する。

> 例) 機能Xの実装のために、モジュールA, B, Cの実装が必要なら、機能Xの実装PRは、モジュールA、B, C の実装PRをそれぞれ作成しstacked PRとすることで、1つながりの機能実装として扱える

「問題解決」の分割を検討する基準を、PRの行数・文字数とする。
具体的な数値はそれぞれ以下とする。

- 行数: 追加と削除の行の合計が200行以下
- 文字数: 2000文字以下

上記を超過するPRに対しては、「問題解決」がさらに詳細な「問題解決」のPRに分割可能かを検討する。検討した結果分割可能な場合は、分割案を提示し、実装者にPRの分割を促す。

## 行数・文字数の測り方

プラグインのルート（このファイルと同じ場所）にある`scripts/diff-size.sh`で測る。パスは引用符で囲む。プラグインのパスには、空白やバックスラッシュが入ることがあるため:

```bash
bash "<プラグインのルート>/scripts/diff-size.sh" <BASE> <HEAD> [<数えないテストのファイル>...]
```

数えないテストのファイルは、リポジトリのルート基準のパスで、1つずつ並べる（下の「テストは数えない」で決める）。

出力は`lines=<行数> bytes=<バイト数>`の1行である。これを上の2つの上限と比べ、どちらかを超えていれば上限超過とする。スクリプトが0以外で終わった場合は、測れなかったものとして扱う。

- 自動生成ファイル（lockfile、Unityの`.meta`など、人が直接編集しないファイル）は数えない。どれが自動生成かは、リポジトリの`.gitattributes`で`linguist-generated`が指定されているかで決める。GitHubがPRの差分で最初から折りたたむのと同じ指定である。独自の除外リストは持たない — 数えたくないファイルがあれば、リポジトリの`.gitattributes`に書いてもらう。
- `.gitattributes`はチェックアウト中のものが読まれる。
- テスト（テストコード、テストの入力データ、evalのように、振る舞いを確かめるためのファイル）は数えない。テストは、プロダクションコードより行数がかさみやすく、テストを数えると、プロダクションコードが小さくても上限を超えてしまうため。どれがテストかは、機械的な規則では決めず、レビューする側が差分を読んで判断する:
  - リポジトリに開発者向けのREADME（`README.md`、`CONTRIBUTING.md`、`docs/`など）があり、テストの置き場や命名が書いてあれば、それに従う
  - 書いていなければ、ファイルの場所・名前・中身から判断する
  - 判断できないファイルは、数える側に入れ、どのファイルが分からなかったかを、結果に添えてユーザーに聞く
  - 数えなかったファイルは、呼び出し元のskillが結果を示す場所に添える。何を外したかが、人から見えるようにするため
  - テストを数えないのは、大きさの上限を測るときだけである。レビュー役は、テストも読んでレビューする
- リネームしただけのファイルは差分が0行になるので、数に入らない。削除したファイルは数に入る。
