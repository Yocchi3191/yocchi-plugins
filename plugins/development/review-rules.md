# レビュー規約

developmentプラグインのskillが、レビューで使う基準をまとめる。基準の値はこのファイルだけに書き、skillはここを読んで判定する。

## PRの大きさの上限

見るべき差分が、次のどちらかを超えたら「上限超過」とする:

- 行数: 追加と削除の行の合計が400行
- バイト数: 追加と削除の行の中身の合計が32,000バイト（1行80桁 × 400行）

### 根拠

人が1回で集中して読める量には目安がある。1時間を超えるレビューは品質が下がり、約200行のPRなら90%が1時間以内にレビューを終えられる。また、400行を超える変更を一度にレビューすると、欠陥を見つける力が下がるという調査（Cisco）がある。これらから、理想的なPRの大きさは200〜400行とされている（出典: https://zenn.dev/isana/articles/ideal-size-of-pull-request-and-why ）。

バイト数も見るのは、Markdownのように1行が1段落になる差分だと、行数が少なくても読む量が多いため。全角文字はUTF-8で3バイトになり、表示幅（2桁）より1.5倍多く数えられる。日本語の多い差分には少し厳しめに働くが、意図した側に倒している。

### 測り方

プラグインのルート（このファイルと同じ場所）にある`scripts/diff-size.sh`で測る。パスは引用符で囲む。プラグインのパスには、空白やバックスラッシュが入ることがあるため:

```bash
bash "<プラグインのルート>/scripts/diff-size.sh" <BASE> <HEAD>
```

出力は`lines=<行数> bytes=<バイト数>`の1行である。これを上の2つの上限と比べ、どちらかを超えていれば上限超過とする。スクリプトが0以外で終わった場合は、測れなかったものとして扱う。

- 自動生成ファイル（lockfile、Unityの`.meta`など、人が直接編集しないファイル）は数えない。どれが自動生成かは、リポジトリの`.gitattributes`で`linguist-generated`が指定されているかで決める。GitHubがPRの差分で最初から折りたたむのと同じ指定である。独自の除外リストは持たない — 数えたくないファイルがあれば、リポジトリの`.gitattributes`に書いてもらう。
- `.gitattributes`はチェックアウト中のものが読まれる。
- リネームしただけのファイルは差分が0行になるので、数に入らない。削除したファイルは数に入る。
