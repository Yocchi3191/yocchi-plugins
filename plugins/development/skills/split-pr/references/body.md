# PRの本文を書く（Step 7）

本文はバッククォートや引用符を含みうるので、リポジトリ外の一時ファイルに書き、`gh pr edit <番号> --title <タイトル> --body-file <一時ファイル>` で書き換える。

## issueの参照

分割するPRの本文から `Closes #<issue>` と `Part of #<issue>` を探し、issueごとに次のとおり書く。参照が無ければ、どのPRにも書かない。上のPRがあれば、その本文の参照は変えない。

- `Closes #<issue>`: 分けたPRのうち一番上のPRにだけ `Closes` を書き、ほか（このPRを含む）は `Part of #<issue>` にする。一番下から順にマージされるので、一番上がマージされたときに全部そろう
- `Part of #<issue>`: 分けたPRをすべて `Part of #<issue>` にする（元のPRがissueの一部だけを扱っていたので、どれもissueを閉じない）

## 対応するREQ

issueの本文に `REQ-<n>:` があれば、このPRが受け持つREQのそれぞれが、分けたPRのどれで満たされるかを決める。このPRの本文に「このPRで対応しているREQ:」の行があれば、受け持つREQはその行のREQだけで、ほかは割り当て直さない。コミットのメッセージ、テストのメソッド名（`REQ_<n>_`）、差分から判断する。**決められないREQがあれば、本文を書く前にユーザーに聞く**（分割後のレビューは、PRごとにここで決めたREQだけを要件にするので、誤ると、ほかのPRのREQが「足りない」と指摘される）。issueの参照やREQが無ければ、割り当てはしない。

## A（元のPR）

本文は全体の説明として残す（設計を示す場所を1か所に残し、分けたPRがぶつ切りにならないようにするため）。issueの参照を上のとおりに直し、末尾に次を足す。

```
## 分割

このPRは大きさの上限を超えたので、stacked PRに分割した。全体の説明はこの本文に残している。

このPRで対応しているREQ: <AのREQ。割り当てをしなかった場合は、この行を省く>

| PR | 対応するREQ | コミット |
|---|---|---|
| #<A>（このPR） | REQ-1, REQ-2 | <短いSHA> <件名>（区切りに入ったコミットを並べる） |
| #<B> | REQ-3 | … |
```

割り当てをしなかった場合は、表の「対応するREQ」の列を省く。

下のPRがあるPR（stackの途中）を分割した場合は、このPRの本文の「全体の説明は #<A> にある」が指すPRがAである。このPRのタイトルと本文は、新しいPRと同じ規則で書き直し、Aの本文の表に新しいPRの行を足す（このPRの行のREQとコミットも直す）。Aのタイトルは変えない。このPRの本文に「全体の説明は #<A> にある」や「このPRで対応しているREQ:」が無ければ（手で組んだstackなど）、どのPRが全体の説明を持つかと、受け持つREQを、書く前にユーザーに聞く。

## B・C…

タイトルは、そのPRに入ったコミットが何をするかを表す。stackの何番目かは書かない（分割のたびに振り直しが要るため）。

```
<issueの参照>

## 概要
<このPRに入ったコミットが何をするかの説明。コミットとその差分から書く>

## 分割

全体の説明は #<A> にある。このPRは、#<A> を分割したstackの1つである。

このPRで対応しているREQ: <このPRのREQ。割り当てをしなかった場合は、この行を省く>

## コミット
- <短いSHA> <件名>
```
