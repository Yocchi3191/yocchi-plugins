# 作業メモの書き方

サイクルの途中で出た設計のアイデアや判断は、作業メモに追記する。置き場がまだ決まっていなければ、この時点で人間に聞く。

追記は1行1件の行動ログにする。作業メモは複数の作業で共有されることがあるので、行頭にブランチ名を付ける。

```
- <ブランチ名> <種別>: <本文>
```

種別は次の3つ。**判断の境目でだけ書く**（毎回のコマンドや編集は、gitで分かるので書かない）。

- `next:` 次にやること。Step 4で人間が次のテストを選んだ直後に、選ばれたREQと着手の理由を1行で書く。Claudeが次を決めて書くことはしない。保留中の論点があれば、同じ行に添える（最後の `next:` しか読まれないため、別の行にしない）。ブランチごとの最後の `next:` だけが有効なので、前の `next:` を消したり直したりしない
- `dead-end:` 試して捨てたこと、採らなかったアイデア。理由も一緒に書く
- `decision:` 選んだ方針。更新したREQは、REQ番号と理由もここに書く

本文は1行80字程度に収める。文の体裁は要らない（読むのは後のClaudeなので、名詞止め・助詞の省略・矢印（→）で詰めてよい）。ただし次の2つは守る。

- 指すものは、リポジトリで引ける識別子で書く（`REQ-3`、テスト名 `issue_<番号>_REQ_<n>_…`、ファイルパスなど）。独自の略語は作らない（読むのは文脈を失った新しいセッションなので、本人にしか分からない略語は復元できない）
- `dead-end:` の理由は削らない。原因を示す語を1つは残す（理由が無いと、同じ道をまた通る）

例:

```
- feat/login next: REQ-3の異常系テスト → 期限切れtokenの扱い未定、先にここ
- feat/login dead-end: auth/session.pyでtoken更新 → 循環import、middlewareへ移す
- feat/login decision: REQ-2のtimeout 30s→10s、モバイル回線の実測が理由
```

長くなるなら要点だけにして、詳細はコードやテスト名に任せる。既存の行は書き換えず、末尾に足すだけにする。
