# Fix Review

PRに付いたレビュー指摘に対応する。レビューそのもの（指摘を出すこと）は`review-pr`の責務であり、このskillは出された指摘を直す側だけを担う。

## Step 1: PR番号は必須

このskillは常にPR番号を必要とする。指定が無ければ求める — 現在のブランチから推測しない。

## Step 2: まだ対応していない指摘を集める

指摘はPR上の3か所に付く。対応済みかどうかの状態と合わせて、1回のクエリですべて取得する:

```bash
gh api graphql -F owner='{owner}' -F repo='{repo}' -F number=<N> -f query='
query($owner:String!,$repo:String!,$number:Int!){
  repository(owner:$owner,name:$repo){
    pullRequest(number:$number){
      comments(first:100){nodes{id url isMinimized body}}
      reviews(first:100){nodes{id url isMinimized state body}}
      reviewThreads(first:100){nodes{id isResolved comments(first:100){nodes{url path line body}}}}
    }
  }
}'
```

- `comments`: PR全体へのコメント。`review-pr`のレビュー結果もここに入る。
- `reviews`: 人がレビューを提出したときの本文（Request changesなど）。
- `reviewThreads`: 差分の行に付いたコメントのスレッド。

`{owner}`・`{repo}`は`gh`が今のリポジトリの値で自動的に埋めるので、そのまま書く。それぞれ100件を超えるPRは想定しない。

**どれが未対応か:** このskillはStep 6で、対応を終えた指摘に「対応済み」の印を付ける — 行コメントのスレッドはresolveし、PR全体へのコメントとレビュー本文は「解決済み」として非表示にする。したがって、次のものが未対応である:

- `comments`・`reviews`: `isMinimized`が`false`のもの
- `reviewThreads`: `isResolved`が`false`のスレッド

時刻では判定しない — 状態で判定すれば、取得後に付いたコメントや、途中で止まった回に拾った指摘も、次の回に正しく未対応として残るため。

このうち、このskill自身の投稿は拾わない。このskillはStep 6で投稿するコメントの本文の1行目に目印を入れる — 対応報告には`<!-- fix-review -->`、行コメントのスレッドへの個別の返信には`<!-- fix-review:reply -->`。1行目がこのどちらかであるコメントは拾わない。「1行目」で判定し「含む」では判定しない — レビュー結果などが目印を引用しただけで、そのコメントを取りこぼさないようにするため。投稿者では見分けない — `review-pr`もこのskillも、ユーザーのGitHubアカウントで投稿するため。

拾うのは指摘と質問。そのどちらとも読めないコメント（お礼、単なる相づちなど）は拾わない。

未対応のスレッドは、最後のコメントまで読む。このskillの返信（1行目が`<!-- fix-review:reply -->`）が付いていて、その後に人のコメントが無ければ、前回返信した後にresolveする前で止まったものである — 返信は済んでいるので、Step 6で返信し直さずresolveだけする。返信の後に人のコメントがあれば、そのコメント（まだ直っていない、など）を新しい指摘・質問として扱う。

**回数を数える:** 次の2つを数えておく。

- 対応の回数: 1行目が`<!-- fix-review -->`のコメントの件数。Step 6の見出しに使う。
- 再レビューの回数: 1行目が`<!-- fix-review -->`で、2行目が`<!-- fix-review:rereview -->`のコメントの件数。このskillが再レビューを頼んだ回の対応報告にだけ付く目印で、質問に答えただけの回、Minorだけを直した回は数えない。今回分割した回は、Importantの指摘に対応した回として数える。「分割済み」とした回は数えない。Step 3とStep 7で、再レビューを続けるかどうかの判断に使う。

未対応の指摘・質問が1件も無ければ、その旨をユーザーに伝えて停止する。

## Step 3: 仕分ける

仕分ける前に、今いるブランチがPRのheadブランチであり、その最新コミットと一致していて、未コミットの変更が無いことを確かめる:

```bash
gh pr view <N> --json headRefName,headRefOid
git branch --show-current
git rev-parse HEAD
git status --porcelain
```

ブランチ名か最新コミットのどちらかが一致しない場合、または`git status --porcelain`が何か出力した場合は、停止してユーザーに伝える — このあと指摘の正誤や「直っている」かを手元のコードで判定するので、レビューされたのと違うコードやpushしていないコミットを根拠にしないため。また、別のブランチに修正を積んだり、ユーザーの作業中の変更を修正のコミットに巻き込んだりするのを防ぐため。勝手にcheckoutもしない（作業ツリーに未コミットの変更があると巻き込むため）。

**stackの下のPRが先に進んでいたら、rebaseする:** このPRがstackの途中にあり（baseブランチが、ほかの開いているPRのheadブランチである）、そのbaseブランチにこのPRが含まない新しいコミットがあれば、このPRのブランチをbaseブランチの上にrebaseしてから仕分ける。下のPRに`fix-review`が修正を積むと、stackの履歴が一直線でなくなり、rebaseするまでstackをマージできないため（出典: https://docs.github.com/en/pull-requests/reference/stacked-pull-requests ）。下のPRの`fix-review`は、Step 7で上のPRもrebaseするが、それが止まって人に任された場合に備えて、ここでも確かめる:

```bash
gh pr view <N> --json baseRefName
gh pr list --head <baseRefName> --state open --json number
git fetch origin <baseRefName>
git merge-base --is-ancestor origin/<baseRefName> HEAD
```

2つ目のコマンドがPRを1件も返さなければ、stackの途中ではないので、rebaseしない（`main`などが進んだだけのPRは、ここでは扱わない）。4つ目のコマンドが成功すれば、baseブランチは先に進んでいないので、rebaseしない。どちらでもなければ、rebaseしてforce pushする:

```bash
git rebase origin/<baseRefName>
git push --force-with-lease=<headRefName>:<headRefOid> origin <headRefName>
```

このrebaseが素直に通るのは、下のPRに修正を足しただけの場合である。下のPRそのものが書き換えられている（trunkの上にrebaseされた、など）と、古い下のPRのコミットまで積み直そうとして、コンフリクトすることがある。rebaseがコンフリクトした場合は、`git rebase --abort`で元に戻して停止し、ユーザーに伝える。force pushが失敗した、または止められた場合も停止し、手元はrebase済みでoriginは元のままであることと、`git reset --hard <headRefOid>`で手元を戻せることを伝える。rebaseした場合は、Step 6の対応報告にその旨を書く。

指摘をそのまま信じない。該当するコードを読んで、指摘が正しいかを確かめてから、次のいずれかに分ける:

- **直す:** 指摘が正しく、直し方が1つに決まるもの。
- **判断が要る:** 次のいずれかに当たるもの。
  - 直し方が複数あり、どれを選ぶかで結果が変わる。
  - PRの範囲に入れるかどうかの判断が要る（別issueに切り出す可能性がある）。
  - 設計・仕様の方針に関わる。
  - 指摘が誤っている、または同意できない（理由を添える）。
  - Critical・Importantの指摘があり、再レビューの回数がすでに2回に達している。レビューと修正が終わらずに繰り返すのを防ぐため、3回目を直すかどうかはユーザーが決める。
  - 直さずに見送りたい。指摘は重さ（Critical / Important / Minor）に関わらず直すのが基本であり、見送るかどうかを勝手に決めない。
  - `review-pr`がPRのサイズの上限超過で付ける「PRを分割する」の指摘。機械的に分けられそうでも、ここに回す。分割するか見送るかはユーザーが決める。分割は新しいブランチやPRを作る作業で、同じブランチにコミット・pushするStep 5では扱えないため、分割すると決まったら`development:split-pr`に渡す（Step 4の「分割する」）。このPRの上にstackで積んだPRがすでにあれば（`gh pr list --base <headRefName> --state open`）、聞くときにそのPRの番号を添え、すでに分割済みかもユーザーに確かめる — `split-pr`を直接起動して分割した場合は、元の指摘に対応済みの印が付かず、ここでまた拾われるため。
  - 過去の対応報告の「見送ったもの」に同じ指摘がある。`review-pr`は前回の判断を知らないため、見送った指摘は再レビューのたびにまた出てくる。勝手に見送り扱いにはせず、前回の見送りの理由を添えて「今回も見送るか」を聞く。
- **直っている:** 前回途中で停止した回のコミットなどで、該当コードがすでに直っているもの。直したコミットを`git log`から探してSHAを控え、Step 6では「直したもの」として報告する。
- **答える:** 質問。コードや会話から答えが分かるものはStep 6で回答する。答えがユーザーの判断や意図に依る場合は「判断が要る」に回す。答えを考えるうちに直すべきだと分かった場合は、指摘として「直す」か「判断が要る」に回す。

「直す」に仕分けたものがあれば、Step 4の前に「こう直す」と一覧でユーザーに見せる。直し方が1つに決まるものは聞かずに進めるためで、異論が出たものだけ「判断が要る」に回す。返事を待たずにStep 4・5へ進んでよい。直し始めた後に異論が来たら、そのコミットを直す項目として扱い、直し方を改めてユーザーに聞く。

## Step 4: 判断が要るものをまとめて聞く

「判断が要る」が1件も無ければ、このステップはスキップする。

直し始める前に、「判断が要る」ものをすべてまとめてユーザーに聞く。1件ずつ聞いて直すことを繰り返さない — 後の判断が先の修正をやり直させる手戻りを防ぐため。ただし「PRを分割する」の指摘があれば、それだけを先に聞き、下の「分割する」と「別のPRへ移った指摘を仕分け直す」を済ませてから、残りをまとめて聞く — 分割で上のPRへ移った指摘について、判断を求めないため。

- 番号付きの箇条書きでチャットに書き、ユーザーに番号で対応させて答えてもらう。途中で送信されることがあるため、答えのない番号は改めて聞く
- 質問UIは使わない。使ってよいのは、yes/noや事実確認のような閉じた質問だけで、推奨ラベルは付けない
- 各項目には、指摘・質問の内容と場所を添える。選択肢は付けず、先にユーザーの考えを自由記述で聞く。選択肢があると、中身を考えずに選ぶ癖がつくため
- ユーザーが「分からない」と答えたら、各案に想定される結果とメリット・デメリットを同じ粒度で付けて、チャットの箇条書きで選択肢を出す。推奨は付けず、並びは中立にし、最後に「それ以外」を置く
- Claudeが根拠を示すときは、既存のベストプラクティスや他者の事例を、出典つきで示す。自分の推論を推奨として出さない。見つからなければ、見つからなかったと言う

回答を受けたら、各項目を「直す」「答える」「見送る」「別issueに切り出す」のいずれかに確定させる。「PRを分割する」の指摘だけは、「分割する」「分割済み」も選べる。分割するとユーザーが決めた場合が「分割する」で、下の「分割する」で扱う。すでに分割済みだとユーザーが答えた場合が「分割済み」で、何もせずStep 6で対応済みの印を付け、対応報告の「分割済みだったもの」に上に積んだPRを並べる。「分割済み」は、今回分割した場合と違い、Importantを直したものとして扱わない — 直接起動された`split-pr`が、分割した後にすでに`review-pr`を回しているため。「別issueに切り出す」と決まったものは、issueのタイトルと本文を下書きしてユーザーに見せ、承認を得てから起票する — 「切り出す」という回答を、起票そのものの承認とはみなさない。下書きが承認されなかった場合は、下書きを直すか、「直す」「答える」「見送る」から選び直してもらう。起票したissueのリンクはStep 6の返信に書く。

### 分割する

「分割する」に決めた指摘が無ければ、この節はスキップする。

ほかの指摘を直す（Step 5）前に、`development:split-pr`をPR番号`<N>`で呼び出す。`fix-review`から呼んでいることを伝える — `split-pr`は、分割した後に再レビューへ進まず、このskillに戻る。先に分割するのは、分割で別のPRへ移ったコードを、このPRで直さないようにするため。

`split-pr`は、新しいPRの番号とURLを返す。分割した後は、下の「別のPRへ移った指摘を仕分け直す」に進む。

`split-pr`が分割を終えずに停止した場合（分け方の判断でユーザーが分割をやめた、pushが止められた、stackを作れなかった、など）は、このskillも停止する。Step 5以降に進まず、`split-pr`が伝えた理由と、まだ対応していない指摘が残っていることをユーザーに伝える。指摘には対応済みの印を付けていないので、このskillをもう一度呼べば、次の回に拾い直される。ただし、`split-pr`がブランチを途中まで組み替えて止まった場合は、手元のHEADがPRのheadと一致せず、Step 3で止まる。`split-pr`が伝えた続け方か戻し方を先に済ませてから、もう一度呼ぶよう伝える。

`split-pr`が分割した後は、手元のブランチが組み替わっている。Step 5では、組み替わった後のこのPRのブランチに修正を積む。

### 別のPRへ移った指摘を仕分け直す

「分割する」で分割したか、「分割済み」に決めた指摘があれば、残りの判断を聞く前に、ほかの指摘を見直す。同じレビュー結果は分割する前の差分全体を見て出ているので、該当するコードがこのPRの上に積んだPRへ移っていることがあるため。どちらも無ければ、この節はスキップする。

移った先の候補は、このPRの上に積んだPRである。「分割する」なら`split-pr`が返した新しいPR、「分割済み」なら`gh pr list --base <headRefName> --state open`で見つかるPRと、さらにその上に積んだPRを使う。

Step 3で仕分けた指摘を、区分を問わず1件ずつ見直す。移ったかどうかは、ファイル単位ではなく、指摘された行の変更が、このPRの差分に含まれるかで判定する — 同じファイルが複数のPRで変更されていることがあるため。このPRの差分は、分岐点から求める:

```bash
gh pr view <N> --json baseRefName
git fetch origin <baseRefName>
git diff $(git merge-base origin/<baseRefName> HEAD)..HEAD
```

- 該当するコードが、このPRに残っている指摘は、Step 3の区分のまま。「判断が要る」ものは、このあとまとめて聞く。
- 該当するコードが上に積んだPRへ移った指摘は、「分割で別のPRへ移った」にする。このPRでは直さず、判断も求めない。Step 6で「該当コードは PR #<番号> に移った」と返信して対応を終える — 移った先のPRのレビューで、改めて扱うため。

## Step 5: 直して、コミット・pushする

「直す」がStep 4の後も1件も無ければ、このステップはスキップする。

手元の状態はStep 3の前に確認済みである。

「直す」ものを1件ずつ直し、1件ごとにコミットする — Step 6の返信で、指摘ごとにどのコミットで直したかを示せるようにするため。そのコミットに含めるのは、その指摘のために変えたファイルだけにする（`git add -A`で他の変更を巻き込まない）:

```bash
git add <その指摘のために変えたファイル>
git commit -m "fix: <直した内容の要約>（PR #<N> レビュー指摘）"
```

コミットしたSHAは、どの指摘に対応するものかと合わせて控えておく（Step 6で使う）。

すべて直したら、プロジェクトにテストがあれば実行し、通ることを確かめてからpushする。テストが落ちた、あるいは実行できなかった場合はpushしない — その旨をユーザーに伝えて停止する（コミットはローカルに残るので、ユーザーが確認できる）。

```bash
git push
```

pushに失敗した場合は、Step 6へ進まず停止してユーザーに伝える — pushされていない修正を「直した」とPRに返信しないため。

テストの失敗やpushの失敗で停止するときは、再開方法も伝える: 原因を解決してpushしたうえで、このskillをもう一度実行する。まだ対応済みの印を付けていないので、指摘は再び未対応として拾われ、すでにコミットした修正はStep 3で「直っている」と判定される。

## Step 6: PRに返信し、対応済みの印を付ける

次の順で進める。投稿・操作に失敗したら、同じ操作を2回までリトライする — 通信の瞬断やAPIの一時的なエラーなら、これで通るため。それでも失敗した場合（認証切れ、権限不足、PRが閉じられた、など）は、Step 7へ進まず停止し、どこまで済んだか（返信・印を付けたもの）と、対応報告の下書きをユーザーに渡す — 印を付けた後に止まると、次の回は拾う指摘が無く、対応報告を出せないため。

本文はどれもバッククォートや引用符を含みうるので、シェルに埋め込まず一時ファイル（リポジトリ外の一時ディレクトリ）に書き出し、`-F body=@<一時ファイル>`（`gh pr comment`では`--body-file`）で渡す。

**1. 行コメントへの個別の返信:** 未対応として拾ったスレッドには、そのスレッドに直接返信する。本文の1行目は目印`<!-- fix-review:reply -->`にし、直したならそのコミットのSHA、答えるならその回答、見送った・別issueに切り出したならその旨と理由（issueのリンク）、分割で別のPRへ移ったなら「該当コードは PR #<番号> に移った」を書く:

```bash
gh api graphql -F threadId=<スレッドのid> -F body=@<一時ファイル> -f query='
mutation($threadId:ID!,$body:String!){
  addPullRequestReviewThreadReply(input:{pullRequestReviewThreadId:$threadId,body:$body}){comment{url}}
}'
```

応答の`comment.url`を控えておく（対応報告から返信へリンクするため）。

**2. 対応済みの印を付ける:** 拾った指摘・質問すべてに印を付ける — 直したものだけでなく、答えたもの・見送ったもの・別issueに切り出したもの・分割したもの・分割済みだったもの・分割で別のPRへ移ったものも。Step 4で全件の扱いを決めているので、ここで印を付けられないものは無い。スレッドはresolveし、PR全体へのコメントとレビュー本文は「解決済み」として非表示にする:

```bash
gh api graphql -F threadId=<スレッドのid> -f query='
mutation($threadId:ID!){resolveReviewThread(input:{threadId:$threadId}){thread{isResolved}}}'
gh api graphql -F id=<コメントまたはレビューのid> -f query='
mutation($id:ID!){minimizeComment(input:{subjectId:$id,classifier:RESOLVED}){minimizedComment{isMinimized}}}'
```

指摘として拾わなかったコメント（お礼など）には印を付けない。

**3. 対応報告:** 最後に、今回の対応全体をまとめたコメントをPRに投稿する。本文の1行目は目印`<!-- fix-review -->`にする。Step 7で再レビューを頼む場合（今回分割した、またはCritical・Importantを直した回で、かつ再レビューの回数が2回未満のとき）は、2行目を`<!-- fix-review:rereview -->`にする。見出しは次のとおりで、該当するものが無い見出しは省く:

- `## レビュー対応（<n>回目）` — `<n>`はStep 2で数えた対応の回数 + 1
- `### 直したもの` — 指摘ごとに、場所・直した内容・コミットのSHA
- `### 見送ったもの` — 指摘ごとに、理由
- `### 別issueに切り出したもの` — 指摘ごとに、issueのリンク
- `### 分割したもの` — 「PRを分割する」の指摘への返答。分割した新しいPRの番号とリンクを並べ、このPRを`review-pr`で再レビューする旨を添える。レビュー結果はPR全体へのコメントで、スレッドへの返信ができないため、ここで返す
- `### 分割済みだったもの` — 「分割済み」とした「PRを分割する」の指摘。上に積んだPRの番号とリンクを並べる。再レビューの一文は付けない
- `### 分割で別のPRへ移ったもの` — 指摘ごとに、移った先のPRのリンク
- `### 質問への回答` — PR全体へのコメントやレビュー本文に書かれた質問への回答。行コメントの質問はスレッドで答えたので、ここには1で控えた返信のURLだけを並べる

```bash
gh pr comment <N> --body-file <一時ファイル>
```

## Step 7: 次に進む

今回このPRにpushし（Step 3のrebaseを含む）、このPRの上にstackで積んだPR（このPRのheadブランチをbaseにする、開いているPR）があれば、先に上のPRをrebaseする — 下のPRにpushすると、上のPRをrebaseするまでstackをマージできないため（出典: https://docs.github.com/en/pull-requests/reference/stacked-pull-requests ）。手元にstackの情報が無ければ、`gh stack rebase`が失敗するので、`gh stack checkout <N>`で取ってきてからやり直す:

```bash
gh stack rebase --upstack
gh stack push
```

rebaseがコンフリクトした、または別のworktreeの変更などで止まった場合は、`gh stack rebase --abort`で元に戻す。pushが失敗した場合も含め、上のPRのrebaseが済んでいないことをユーザーに伝え、rebaseは人に任せる。この後の再レビューやreadyへの切り替えは、そのまま進める。

今回直したものに、Critical・Importantの指摘が含まれるかで分ける。「PRを分割する」の指摘を分割したときは、Importantを直したものとして扱う — 分割した後の差分が上限内に収まったかを、`review-pr`に測り直させるため。重さの付いていない指摘（人のコメントなど）はMinorとして扱う。

- **Critical・Importantを直した場合:** 直した結果を確かめるため、再レビューする。
  - Step 2で数えた再レビューの回数が2回未満なら、`development:review-pr`をPR番号`<N>`で呼び出す。
  - 2回に達していれば（Step 4でユーザーが3回目の修正を選んだ場合）、再レビューせずに停止する。対応報告のURLと、まだ再レビューを通っていない旨を伝える。
- **Minorだけを直した、または直したものが無い場合:** 再レビューはしない。PRがDraftなら、ready for reviewに切り替える:

```bash
gh pr view <N> --json isDraft -q .isDraft
gh pr ready <N>
```

  すでにDraftでなければ切り替えは不要。直していないCritical・Importantが残っていてもreadyにする — 残っているのは、見送る・別issueに切り出す・3回目を直さないのいずれかをStep 4でユーザーが決めたもの、または分割で別のPRへ移ったものだけだから。最後に、対応報告のURLをユーザーに伝える。
