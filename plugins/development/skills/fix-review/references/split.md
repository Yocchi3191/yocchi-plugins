# PRの分割（「PRを分割する」の指摘）

レビューで、PRのサイズが目安を超えているとして「PRを分割する」の指摘が付くことがある。機械的に分けられそうでも、**分割するか見送るかはユーザーが決める**（Step 4で、ほかの指摘より先に聞く）。分割は新しいブランチやPRを作る作業で、同じブランチにコミット・pushするStep 5では扱えないため、分割すると決まったら `development:split-pr` に渡す。

聞くときは、このPRの上にstackで積んだPRがすでにあるか（`gh pr list --base <headRefName> --state open`）を確かめ、あれば番号を添えて「すでに分割済みか」も聞く。`split-pr` を直接起動して分割した場合、元の指摘に対応済みの印が付かず、ここでまた拾われるため。

回答は「分割する」「分割済み」「見送る」のどれかに確定させる。

## 分割する

ほかの指摘を直す（Step 5）前に、`development:split-pr` をPR番号で呼ぶ。`fix-review` から呼んでいることを伝える（`split-pr` は、分割後に再レビューへ進まず、このskillへ戻る）。先に分割するのは、別のPRへ移ったコードをこのPRで直さないため。`split-pr` は新しいPRの番号とURLを返す。分割後は、下の「別のPRへ移った指摘を仕分け直す」に進む。また、手元のブランチが組み替わっているので、Step 5では組み替わった後のブランチに修正を積む。

- ユーザーが分け方の判断で分割をやめた: 分割の指摘を「見送る」に確定させ、残りの対応に進む。対応報告の「見送ったもの」に理由を書く
- `split-pr` が分割を終えずに停止した（pushが止められた、stackを作れなかった、など）: このskillも停止する。Step 5以降に進まず、`split-pr` が伝えた理由と、指摘が残っていることを伝える。指摘に印は付けていないので、もう一度呼べば次の回に拾い直される。`split-pr` がブランチを途中まで組み替えて止まった場合は、手元のHEADがPRのheadと一致せずStep 3で止まるので、`split-pr` が伝えた続け方か戻し方を先に済ませてから呼び直すよう伝える

## 分割済み

何もせず、Step 6で対応済みの印を付ける。対応報告の「分割済みだったもの」に、上に積んだPRを並べる。「分割する」と違い、Importantを直したものとして扱わない（直接起動された `split-pr` が、分割後にすでに `review` を回しているため）。

## 別のPRへ移った指摘を仕分け直す

「分割する」で分割した、または「分割済み」と決めた指摘があれば、残りの判断を聞く前に、ほかの指摘を見直す。同じレビュー結果は分割前の差分全体を見て出ているので、該当コードが上に積んだPRへ移っていることがあるため。

移った先の候補は、上に積んだPR（「分割する」なら `split-pr` が返したPR、「分割済み」なら `gh pr list --base <headRefName> --state open` で見つかるPRと、さらにその上のPR）。

仕分けた指摘を、区分を問わず1件ずつ見直す。移ったかどうかは、ファイル単位ではなく、**指摘された行の変更が、このPRの差分に含まれるか**で判定する（同じファイルが複数のPRで変更されうるため）。「分割する」なら、指摘の行番号は分割前のhead（`headRefOid`）のファイルを指すので、そのコミットで該当行を確かめる。「分割済み」なら、行番号がどのコミットを指すか分からないので、内容とファイル名から推測し、推測できなければこのPRに残っているものとして扱う。このPRの差分は分岐点から求める:

```bash
gh pr view <N> --json baseRefName
git fetch origin <baseRefName>
git diff $(git merge-base origin/<baseRefName> HEAD)..HEAD
```

- 該当コードがこのPRに残っている: 区分はそのまま（判断が要るものは、このあとまとめて聞く）
- 上に積んだPRへ移った: 「分割で別のPRへ移った」にする。このPRでは直さず、判断も求めず、Step 6で「該当コードは PR #<番号> に移った」と返して対応を終える（移った先のレビューで改めて扱うため）
