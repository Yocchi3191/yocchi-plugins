# 仕分け・質問・コミットの細則（Step 3〜5）

## Step 3: 手元の確認と仕分け

```bash
gh pr view <N> --json headRefName,headRefOid
git branch --show-current
git rev-parse HEAD
git status --porcelain
```

ブランチ名か最新コミットが違う、または未コミットがあれば停止する。

指摘を読んで正しいか確かめ、次に分ける。

- **直す:** 正しく、重く、直し方が1つに決まる
- **対応しない:** 軽い（直さなくても害が小さい）、または指摘が誤り・同意できない。人のコメントでも同じ。Step 6で理由を返す。再レビューでまた出ても、聞き直さず同じ扱いにする。ユーザーが見送った・別issueに切り出した指摘が再び出たときも同じ。過去の対応報告（1行目が`<!-- fix-review -->`のコメント）の「見送ったもの」「別issueに切り出したもの」と照らし、同じ指摘なら前回の理由を返す
- **判断が要る（ユーザーに聞く）:** 次に当たるものだけ。これ以外は、聞かずに自動で進める
  - 設計判断（構造・インターフェースの方針）
  - 仕様の判断（挙動の決め方、ユーザーの意図に依る質問への答え）
  - 手戻りになりそうなもの（直し方が複数で結果が変わる、PRの範囲に入れるか・別issueにするか、再レビューが2回に達しているのにCritical・Importantがある、「PRを分割する」の指摘＝`split.md`）
- **直っている:** すでに直っている。直したコミットのSHAを`git log`から探して控え、「直したもの」として報告する
- **答える:** 質問。答えが分かれば回答する。ユーザーの意図に依るなら「判断が要る」へ

「直す」ものは、Step 4の前に「こう直す」と一覧で見せる。返事は待たずに進んでよく、異論が来たらそのコミットを直す項目として聞き直す。

## Step 4: まとめて聞く

- 番号付きの箇条書きで、各項目に指摘内容と場所を添え、番号で答えてもらう。答えのない番号は改めて聞く。質問UIは使わない（yes/noだけ可。推奨ラベルは付けない）
- 選択肢は付けず、先に自由記述で聞く（選択肢があると考えずに選ぶため）
- 「分からない」と言われたら、各案の想定結果とメリット・デメリットを同じ粒度で出し、推奨は付けず、最後に「それ以外」を置く。根拠は出典つき。自分の推論を推奨にしない。出典が見つからなければ、見つからなかったと言う
- 回答を「直す」「答える」「見送る」「別issueに切り出す」に確定させる。別issueは、タイトルと本文を下書きして見せ、承認を得てから起票する（「切り出す」という回答を起票の承認とはみなさない。下書きが承認されなければ、直すか選び直してもらう）

## Step 5: コミット

1件ごとにコミットする（その指摘のファイルだけadd。`git add -A`は使わない）:

```bash
git add <その指摘のために変えたファイル>
git commit -m "fix: <直した内容の要約>（PR #<N> レビュー指摘）"
```

SHAは、どの指摘に対応するかと合わせて控える。すべて直したら、プロジェクトにテストがあれば実行し、通ってから`git push`する。テストが落ちた・実行できない、またはpushに失敗したら、pushせず（pushの失敗なら返信せず）停止する。再開は、原因を解決してpushしてから、もう一度呼ぶ。印を付けていないので指摘は再び拾われ、コミット済みの修正は「直っている」と判定される。
