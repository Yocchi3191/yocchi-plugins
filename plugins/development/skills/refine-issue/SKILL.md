# Refine Issue

issueを、実装に渡しても成果物がぶれない状態に固める。`development:design`は「要件が固まった後」に呼ばれるため、固める作業はこのskillが受け持つ。

**検証できない文は、まだ仕様になっていない。** 条件の各文が、そのままテストの形（「〜のとき〜になる」）に書き直せるかを基準にする。

書式はこのskillのテンプレートで統一し、プロジェクト側のテンプレートには合わせない。

## 作業の型

- 挙動を決める作業（新機能、既存の挙動の変更）は`enhancement`のissueを書く
- 期待どおりに動かない不具合は`bug`のissueを書く
- リファクタなど、挙動を変えない作業はissueを書かず、PRだけにする。このskillの対象外

## Step 1: issueを読む

対象issueの本文とラベルを取得する。

```bash
gh issue view <番号> --json title,body,labels
```

取得に失敗した場合は、番号の確認をユーザーに頼んで停止する。本文が空でも停止せず、タイトルだけを手がかりに先へ進む。

## Step 2: 種別を判定する

ラベルから種別を決める。

- `enhancement` → 新機能。このSKILL.mdと同じディレクトリの`issue-feature.md`を使う
- `bug` → バグ。このSKILL.mdと同じディレクトリの`issue-bug.md`を使う
- 両方付いている → どちらで進めるかをユーザーに確認する
- どちらもない → 本文から種別を推測してユーザーに確認し、承認を得てからラベルを付ける。リファクタなど挙動を変えない作業だと分かったら、issueは不要であることを伝えて終了する

使うラベル（`enhancement` / `bug`）がリポジトリに無いときは、次を確認する。

```bash
gh label list --json name -q '.[].name'
```

無ければ、このskillの書き方に必要であることを伝えて、足してよいかユーザーに聞く。承認を得たら作る。

```bash
gh label create <名前> --description "<説明>"
```

ラベルが揃ったら、承認を得た種別のラベルを付ける。

```bash
gh issue edit <番号> --add-label <名前>
```

ラベルの一覧の取得・作成・付与に失敗した場合は、失敗内容を伝え、ラベルなしで本文の整形だけを続けるか、ユーザーに聞く。

## Step 3: テンプレートと照らして調べる

選んだテンプレートの各欄について、次の2点を確認する。

- 欄が埋まっているか。埋まっていない欄を控える。本文に書かれている材料を整理すれば埋められる欄は、下書きしてStep 6で承認を求める。材料が無い欄は、推測で埋めずに控える。ユーザーが理解していない中身を、Claudeが書いてしまわないため
- 条件（`REQ-<n>:`）の各文が、「〜のとき〜になる」の形に書き直せるか。書き直せない文（「使いやすい」「面白い」など）は「検証できない」として控える

## Step 4: 抜けを洗い出す

issueに書かれていない次の点を、Claudeが推測して控える。

- 異常系（入力が不正、相手が応答しない、権限がない）
- 境界（0件、1件、上限）
- 壊れたときの被害が大きいところ（データ削除、課金、認証）
- 既存の仕様を置き換える変更か。置き換えるなら、置き換え元（`#<番号>` の `REQ-<n>`）と、変える理由を確認する

## Step 5: 足りない情報を聞く

Step 3・4で控えたもののうち、issueやコードを読んでも決められないものだけをユーザーに聞く。調べれば分かることは聞かない。

- 本文が空のときは、テンプレートの上の欄から順に、1欄ずつ自由記述で聞く。材料はユーザーが出し、Claudeはそれを整理するだけにする
- 妥当な選択肢が1つに決まるものは、聞かない。「こう決める」と一覧で見せ、異論がなければ進める
- 妥当な選択肢が複数あるものは、質問UIを使わず、チャットで先にユーザーの考えを自由記述で聞く。選択肢があると、中身を考えずに選ぶ癖がつくため
- 複数の質問は、番号付きの箇条書きでまとめて聞き、ユーザーに番号で対応させて答えてもらう。途中で送信されることがあるため、答えのない番号は改めて聞く
- ユーザーが「分からない」と答えたら、各案に想定される結果とメリット・デメリットを同じ粒度で付けて選択肢を出す。推奨は付けず、並びは中立にし、最後に「それ以外」を置く
- Claudeが根拠を示すときは、既存のベストプラクティスや他者の事例を、出典つきで示す。自分の推論を推奨として出さない。見つからなければ、見つからなかったと言う
- 質問UIを使ってよいのは、yes/noや事実確認のような閉じた質問だけ。推奨ラベルは付けない
- 「検証できない」と控えた文は、測れる形に分解できないかをユーザーと考える（例:「使いやすい」→「ホームから目的の機能まで<n>操作以内」）。分解できないものは、人間の動作確認かレビューに回す扱いにする。そのREQには、コロンの後ろに`[人間確認]`の印を付け（例: `REQ-3: [人間確認] …`）、確認方法をノート欄に書く
- 控えた事項がすべて片付くまで続ける。切り上げを勧めない。ユーザーから打ち切られたら、片付いていない事項を「未解決」として本文に明記してStep 6へ進む

## Step 6: 本文への反映案を見せて、承認を得る

テンプレートに沿って整えた本文を、差分として見せる。ユーザーの承認を得てから反映する。

- 条件は`REQ-<n>:`を頭に付けた1行ずつの列挙にし、条件だけを書く。テスト名の`issue_<番号>_REQ_<n>_…`（識別子にハイフンは使えないため、アンダースコア区切り）から、この条件に辿れるようにするため
- 理由は列挙に混ぜず、概要の欄に書く

本文はバッククォートや引用符を含みうるので、シェルに埋め込まず、リポジトリ外の一時ディレクトリに書き出して渡す。反映したら、その一時ファイルは削除する。

```bash
gh issue edit <番号> --body-file <一時ファイル>
```

反映に失敗した場合は、失敗内容を伝え、本文の案をそのまま提示して、手動での反映を頼む。
