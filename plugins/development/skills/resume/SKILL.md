# Resume

作業の現在地を、要約ではなく「食い違い」で示す。要約は書いた時点で古くなるため。確認できた事実と、事実同士のずれだけを根拠付きで出す。

このskillは何も書き込まない（例外は、Step 2の `git fetch` だけ）。進捗ファイルも作らない。情報源は、git・issue・PR・既存のメモ（`impl`の行動ログを含む）だけ。行動ログは書き手の主張なので、必ずgitとテストで検証する。

## Step 1: 作業の単位を決める

現在のブランチ名と、その作業にあたるissue番号・PR番号を探す。

```bash
git branch --show-current
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
gh pr list --head "$(git branch --show-current)" --state all --json number,title,isDraft,state
```

2行目の出力を、以降`<default>`として使う。

- detached HEADなら、名前付きブランチが要ると伝えて停止する
- ブランチ名・PR本文・直近のコミットにissue番号があれば、それを使う
- 見つからなければ聞き、「無い」ならREQ照合を省く
- デフォルトブランチ上で作業ブランチが無ければ、「着手中の作業は見当たらない」と伝え、未着手のissueを数件示して停止する

## Step 2: 状態を集める

読み取り専用で、次を集める。取得できないものは「分からない」として扱い、推測で埋めない。

- **git:** 先に `git fetch` でリモートの参照を最新にする。その上で、未コミットの変更（`git status --short`）、デフォルトブランチからの差（`git log --oneline origin/<default>..HEAD`）、リモートとの差（`git rev-list --left-right --count '@{u}...HEAD'`。upstreamが無くて失敗したら、未pushとして扱う）
- **issue:** `gh issue view <番号> --json title,body` で `REQ-<n>:` の一覧を取る
- **テスト:** テストのコードを `issue_<番号>_REQ_<n>_` で検索し、REQごとの有無を調べる。テストを実行はしない
- **PR:** あれば、Draftかどうか、未対応のレビュー指摘（`fix-review` の「まだ対応していない指摘を集める」と同じ基準で判定する）、CIの状態、本文の `## 動作確認` のチェック状態
- **ADRメモ:** `design` が残したもの。リポジトリルートの `docs/adr/<ブランチ名>.md`、`doc/adr/<ブランチ名>.md` の順に探し、無ければ無しとして扱う
- **行動ログ:** `impl` が作業メモに追記した、`<ブランチ名> <種別>: <本文>` 形式の行。置き場はCLAUDE.mdに従い、記載もファイルも無ければ聞かずログ無しとして扱う。読むのは次の分だけ:
  - 現在のブランチ名の行のうち、末尾20行
  - 現在のブランチの最後の `next:` 1行（20行より前にあっても読む）
  - 全体は読まず、次のように取り出す（`-F`でブランチ名を文字列のまま照合し、後ろの空白まで含めて `feat/login` が `feat/login-v2` に一致しないようにする）:
    ```bash
    grep -F -- "- <ブランチ名> " <作業メモ> | tail -n 20
    grep -F -- "- <ブランチ名> next:" <作業メモ> | tail -n 1
    ```

## Step 3: 食い違いを探す

集めた事実を突き合わせ、ずれを拾う。例:

- REQにテストが無い、またはテストがあるのにREQが無い（REQ更新の可能性）
- 未コミットの差分があるのに、最後のコミットから時間が経っている
- ADRメモが残っているのに、PRがすでにある（submitの展開漏れ）
- PRがDraftのまま、未対応の指摘がある、またはCIが赤い
- PR本文の `## 動作確認` に、チェックの付いていない `- [ ] REQ-<n>`（`[人間確認]` のREQ）が残っている
- 最後の `next:` が指す作業が、すでに済んでいる、またはコードに見当たらない。ただし、済んでいて、テストの無いREQ（`[人間確認]` を除く）も残っていなければ、食い違いにせず「implは完了。次は人間確認か `submit`」として扱う
- 最後の `next:` と実際のコミット・差分、またはログの `decision:` と実際のコード・ADRメモが、大きく食い違っている

見つけた食い違いは、事実（何を見たか）と、そこから言えること、言えないことを分けて書く。「たぶんこうだろう」は事実として書かない。食い違いが1つも無ければ、そう言って、残りのREQを示すだけにする。

## Step 4: 報告する

次の形で、短く出す。

1. **作業の単位:** ブランチ・issue・PR
2. **食い違い:** 各項目に根拠を添える。重要そうな順に、多くても5件まで
3. **前回の続き:** 最後の `next:` があれば、そのまま1行で引用する。食い違いがあれば、そこに注記する。`dead-end:` のうち今回の候補に関わるものは、同じ道を繰り返さないよう1行添える。作業メモが無ければ「読んでいない」と書く
4. **着手の候補:** 2〜3個。各候補に理由と、使うskill（`impl`・`fix-review`・`submit` など）を書く。1つに絞らない

候補は、食い違いから素直に出るものを挙げる。「これが最善」とは言わない。選ぶのはユーザーで、選ばれたらそのskillに引き継ぐ。自分では実装も修正もしない。

食い違いが毎回同じ種類で出るなら、前段のskillが残すべきものを残していない可能性がある。その場合は、候補の末尾に1行だけ添える。
