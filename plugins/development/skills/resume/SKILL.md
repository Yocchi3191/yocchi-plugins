# Resume

作業の現在地を、要約ではなく「食い違い」で示す。要約は書いた時点で古くなり、AIが書くともっともらしく外れるため。確認できた事実と、事実同士のずれだけを根拠付きで出す。

このskillは何も書き込まない（例外は、Step 2でリモートの参照を最新にする `git fetch` だけ）。進捗ファイルも作らない — 保存した進捗の要約は必ず古くなる。情報源は、git・issue・PR・既存のメモ（`impl`が追記する行動ログを含む）だけである。行動ログは追記専用の事実の記録であり、要約ではない。ただし書き手の主張なので、必ずgitとテストで検証する。

## Step 1: 作業の単位を決める

現在のブランチ名と、その作業にあたるissue番号・PR番号を探す。

```bash
git branch --show-current
gh repo view --json defaultBranchRef -q .defaultBranchRef.name
gh pr list --head "$(git branch --show-current)" --state all --json number,title,isDraft,state
```

2行目の出力を、以降`<default>`として使う。

- ブランチ名が空（detached HEAD）なら、名前付きブランチが要ると伝えて停止する
- ブランチ名・PR本文・直近のコミットメッセージにissue番号があれば、それを使う
- 見つからなければ、ユーザーにissue番号を聞く。「無い」と答えられたら、issueなしで進める（Step 3のREQ照合は省く）
- デフォルトブランチ上にいて作業ブランチが無ければ、「着手中の作業は見当たらない」と伝え、未着手のissueを `gh issue list` で数件示して停止する

## Step 2: 状態を集める

読み取り専用で、次を集める。取得できないものは「分からない」として扱い、推測で埋めない。

- **git:** 先に `git fetch` でリモートの参照を最新にする（作業ツリーには触れないので、このskillで許す唯一の書き込みとする）。その上で、未コミットの変更（`git status --short`）、デフォルトブランチからの差（`git log --oneline origin/<default>..HEAD`）、リモートとの差
- **issue:** `gh issue view <番号> --json title,body` で `REQ-<n>:` の一覧を取る
- **テスト:** テストのコードを `issue_<番号>_REQ_<n>_` で検索し、REQごとの有無を調べる。テストを実行はしない
- **PR:** あれば、Draftかどうか、未対応のレビュー指摘（`fix-review` の Step 2 と同じ基準で判定する。条件はここに書き写さない）、CIの状態、本文の `## 動作確認` のチェック状態
- **ADRメモ:** `design` が残したもの。リポジトリルートの `docs/adr/<ブランチ名>.md`、`doc/adr/<ブランチ名>.md` の順に探し、どちらも無ければADRメモ無しとして扱う
- **行動ログ:** `impl` が作業メモに追記した、`<ブランチ名> <種別>: <本文>` 形式の行。置き場はプロジェクトのCLAUDE.mdに書いてあればそれを使い、無い、またはファイルが無ければ、聞かずにログ無しとして扱い、Step 4でそう伝える。読むのはコンテキストを膨らませないため、次の分だけにする:
  - 現在のブランチ名の行のうち、末尾20行
  - 現在のブランチの最後の `next:` 1行（20行より前にあっても読む）
  - ファイル全体は読まない。次のように該当行だけを取り出す（`-F`でブランチ名を文字列のまま照合し、後ろの空白まで含めて`feat/login`が`feat/login-v2`に一致しないようにする）:
    ```bash
    grep -F -- "- <ブランチ名> " <作業メモ> | tail -n 20
    grep -F -- "- <ブランチ名> next:" <作業メモ> | tail -n 1
    ```
  - ログは本人の主張であり、事実ではない。Step 3でgitやテストと突き合わせて検証する

## Step 3: 食い違いを探す

集めた事実を突き合わせ、ずれを拾う。例:

- REQにテストが無い、またはテストがあるのにREQが無い（REQが後から更新された可能性）
- 未コミットの差分があるのに、最後のコミットから時間が経っている
- ADRメモが残っているのに、PRがすでにある（`submit` が展開し忘れた可能性）
- PRがDraftのまま、未対応の指摘がある、またはCIが赤い
- PR本文の `## 動作確認` に、チェックの付いていない `- [ ] REQ-<n>`（`[人間確認]` のREQ）が残っている
- 最後の `next:` が指す作業（テスト、REQなど）が、すでに済んでいる、またはコードに見当たらない。ただし、済んでいて、テストの無いREQ（`[人間確認]` を除く）も残っていなければ、食い違いにせず「implは完了。次は人間確認か `submit`」として扱う（`impl` は全REQを終えたとき `next:` を書かないため）
- 最後の `next:` と、実際のコミット・差分でやっていることが大きく違う
- ログの `decision:` と、実際のコード・ADRメモが食い違っている

見つけた食い違いは、事実（何を見たか）と、そこから言えること、言えないことを分けて書く。「たぶんこうだろう」は事実として書かない。食い違いが1つも無ければ、そう言って、残りのREQを示すだけにする。

## Step 4: 報告する

次の形で、短く出す。

1. **作業の単位:** ブランチ・issue・PR（見つかった範囲）
2. **食い違い:** 各項目に根拠（コミット、ファイル、コメントのURLなど）を添える。重要そうな順に、多くても5件まで
3. **前回の続き:** 最後の `next:` があれば、そのまま1行で引用する。食い違いがあれば、そこに注記する。`dead-end:` のうち今回の候補に関わるものは、同じ道を繰り返さないよう1行添える。作業メモが見つからなかったときは「作業メモが見つからなかったので読んでいない」と1行書く
4. **着手の候補:** 2〜3個。各候補に理由と、使うskill（`impl`・`fix-review`・`submit` など）を書く。1つに絞らない

候補は、食い違いから素直に出るものを挙げる。「これが最善」とは言わない。どれから始めるかは、ユーザーが選ぶ。選ばれたら、そのskillに引き継ぐ — このskill自身は実装も修正もしない。

## 注意

- 要約を書かない。「全体として順調です」のような、根拠に辿れない文を出さない
- 何も保存しない。メモもブランチもコミットも作らない
- 食い違いが毎回同じ種類で出るなら、前段のskillが残すべきものを残していない可能性がある。その場合は、候補の末尾に1行だけ添える
